# Route experiment: do real agents gain anything from deterministic editing?

Status: **Runs 1–3 done** (30 in-session runs; see Results). Every run in every arm was correct, including Run 3's
rename of 241 sites in 110 files. The runs show tool selection and overhead, not an effectiveness difference. No run
used Map + Edit. On the large case, agents applied the edits in bulk, and four of six reported writing their own
throwaway type-resolution script. Preparing Run 2
found four defects in the Map + Edit route itself (see Follow-ups); all are fixed in agent-edit 0.8.1 and agent-map
0.24.1/0.24.2.

## Question

The [route benchmark](../README.md#route-benchmark) measures the mechanical part of each editing route. It shows
where Map + Edit needs fewer bytes and calls, and where native editing is cheaper. It cannot say whether a real
coding agent is more correct, cheaper or faster with these tools, or whether it picks the right route unprompted.
This experiment asks exactly that. The routing table below is a **hypothesis to test**, not a policy:

| Operation | Hypothesised best route |
| --- | --- |
| Business logic, new implementation, local bug fix | native |
| Exact declaration removal, guarded anchored mutation | direct |
| Cross-file rename, symbol relocation, dependency-aware refactoring | Map + Edit |
| Verification | every route |

No mandatory routing, new runtime abstraction or permanent prompt instruction follows from this document until the
results warrant it. A result where agents choose well without guidance argues against building routing at all.

## Arms

The task text is identical in every arm, and so is the case source tree (`case_source_digest` in each manifest).

| Arm | Workspace (`tools/route-experiment/prepare.py`) |
| --- | --- |
| **A** native | The case tree only: a fresh single-commit repository with no remote and no history. |
| **B** optional | A, plus released `voku/agent-edit` and `voku/agent-map` (exact versions in `cases.json`) in an isolated `tools/route-tools` Composer project. Nothing mentions them. |
| **C** guided | B, plus one `AGENTS.md` section naming the two binaries and containing `agent-edit instructions --format=text`, about 3 KB. Its size is recorded as `instruction_overhead_bytes`. |

The workspace layout (`manifest.json`, `task.md`, `repo/`) is the one agent-loop's
[`tools/learning-effect/run-arm.sh`](https://github.com/voku/agent-loop/blob/main/tools/learning-effect/run-arm.sh)
runs. That script is reused unchanged, with the same frozen envelope, Bash network sandbox and probe, and the same
rule against deleting runs. agent-edit itself makes no model calls.

## Cases

| Case | Kind | What makes it hard |
| --- | --- | --- |
| `fixture-rename` | adversarial | Rename `Invoice::total()` while `Cart::total()` is called on the same line; a SQL string, an array key and a comment also contain `total`. |
| `fixture-remove` | adversarial | Remove an unused private method and leave everything else byte-equivalent in code. |
| `fixture-body` | local implementation | A business-logic change (ignore negative lines) in one method. Native editing is expected to win. |
| `recall-rename` | real code | Rename the public `SelectionResult::toRecallResult()` in voku/agent-recall-compiler at `ad580ac`. It has 4 callers in 4 files, and the full PHPUnit suite must stay green. |
| `hierarchy-rename` (Run 2) | adversarial | Rename the interface method `PriceSource::amount()` across 4 implementations and overrides, including a `parent::amount()` call. Calls reach the family only through repository return types, closures and a nullable local; unrelated `Coupon::amount()` and `GiftCard::amount()` are called on the same lines. A `$amount` property, an `'amount'` key and constant, and a comment also stay. Generated by `fixtures/hierarchy_rename.py`. |
| `scale-rename` (Run 3) | adversarial | Rename `Ledger\Entry::value()` in a generated code base of 132 files: 13 implementations and overrides (6 through `parent::`) and 227 of about 400 `->value()` calls in 100 services. 8 unrelated `Config` classes also declare `value()`. Each receiver's type is known only through a neutral navigator method (`->journal(2021)->latest(3)->value()`), and the same method name returns a ledger entry in one navigator and an unrelated class in another. Generated by `fixtures/scale_rename.py`. |
| `recall-collect-rename` (Run 2) | real code | Rename `RecallProvider::collect()` at `ad580ac`: the interface, 10 providers, 2 anonymous test providers and about 50 calls in 25 files, next to unrelated `collectResult`-style helpers. Suite and PHPStan available. |

The Run 1 fixture is emitted by `tools/route-benchmark.php --fixture=DIR`, so the experiment and the benchmark use the
same files. The Run 2 cases use `oracles/token-rename.php`: every PHP file must match the expected rename by code
tokens (comments and whitespace ignored), and for `hierarchy-rename` both trees must also print the same output. The
check is by tokens because the plausible native shortcut keeps behaviour: rename every `->amount(` and every
`function amount(`, and PHP still runs, but the unrelated `Coupon` and `GiftCard` API is renamed too.

**Historical refactorings.** A scan of agent-loop (2,810 commits), agent-map and agent-edit did not find a commit
that is a pure mechanical rename. The scan looked for commits where one method or call name disappears and another
appears in two or more files. Renames in these repositories always came bundled with behaviour changes, such as
agent-loop `01edde10f5`, which merges `RelativePath::fromRoot()` into `PathResolver::relativeTo()` with new
separator normalisation. A historical commit therefore cannot serve as a clean oracle, so the real-code case is a
designed task on a real code base. More cases are added through `cases.json` with their own oracle.

## Oracles and isolation

Oracles live in `tools/route-experiment/oracles/` and never enter a workspace. They check behaviour by executing the
final tree, check identity (old name gone, new name declared, unrelated symbols untouched), and for `recall-rename`
run the suite. Source changes beyond the rename are reported as unintended changes, not counted as incorrect. The
isolation rules of the agent-loop experiments apply unchanged:

- Run each arm in a disposable container that holds only its `<out>` directory; Read, Glob and Grep can read the
  whole disk.
- Grade only in a disposable environment, because grading executes candidate-written code.

## Measures (`tools/route-experiment/grade.py`)

| Measure | Definition |
| --- | --- |
| first-pass correctness | Oracle (and suite, where a case has one) passes on the final tree. |
| unintended changes | Changed paths outside the case's `allowed_paths`; tool state and installs excluded. |
| chosen route | From the transcript: Bash calls of `agent-map` and `agent-edit`, and Edit/Write calls. Reported as `map+edit`, `direct`, `native` or `none`. Measured in every arm, so B shows unprompted selection. |
| retries | Failed tool results (`is_error`). |
| tokens, turns, duration, cost | From the stream-json `result` event; `null` when the host does not report them. Input tokens include cache reads and writes. |
| instruction overhead | Bytes of the arm C guidance section. |
| cost per success | Cost of a run that is correct; failed runs are kept in the ledger. |

Comparisons fixed before any run:

1. **B vs A** on every case: does merely installing the tools change correctness or cost, and which route does an
   agent choose unprompted?
2. **C vs B:** does about 3 KB of guidance pay for its own tokens, and does it move route choice towards the
   hypothesis?
3. **Per case kind:** the adversarial and real-code renames are where Map + Edit is expected to help. On
   `fixture-body`, any arm that does worse than A is a cost of the tooling and is reported as such.

Schedule: 4 cases × 3 arms × 3 repetitions = 36 runs. They run in an order shuffled with a recorded seed, each with a
new session and a new workspace. Negative and failed runs are kept and graded.

## Procedure

```bash
kit=tools/route-experiment
python3 $kit/prepare.py --case fixture-rename --arm B --out runs/fr-B-1
../agent-loop/tools/learning-effect/run-arm.sh runs/fr-B-1 <model-id>
python3 $kit/grade.py --out runs/fr-B-1 --ledger docs/route-experiment.results.jsonl
```

`recall-rename` needs `--source` pointing at a clone of voku/agent-recall-compiler that contains `ad580ac`.

**In-session runs without Composer access** (as in Run 1) replace the Composer installs with one prepared runtime:

```bash
python3 $kit/prepare.py --case fixture-rename --arm C --out runs/fixture-rename-C --no-composer --tools-runtime RUNTIME
python3 $kit/prepare.py --case recall-rename --arm A --out runs/recall-rename-A --no-composer --source ../agent-recall-compiler \
  --vendor-shim RUNTIME --extra-psr4 'voku\AgentLearning\=PATH/agent-learning/src/'
```

`RUNTIME` is an agent-edit checkout at the pinned release with its `vendor/`. Run each arm with a fresh agent, record
the host's usage report in `<out>/run.json` (`ran`, `total_tokens`, `tool_uses`, `duration_ms`), then grade.

CI runs `python3 tools/route-experiment/calibrate.py` on every change. It prepares arm A of every case and grades
four kinds of simulated outcome, with no model run:

| Outcome | Expected verdict |
| --- | --- |
| untouched workspace | incorrect |
| reference solution | correct |
| reference plus a stray file | one unintended path |
| plausible native shortcut on `fixture-rename` | incorrect, with `src/Cart.php` unintended |
| plausible native shortcut on `hierarchy-rename` | incorrect, with `src/Promo/Coupon.php` and `src/Promo/GiftCard.php` unintended |
| plausible native shortcut on `scale-rename` | incorrect, with every `src/Config` class among the unintended paths |

## Results

### Run 1 (2026-11-19, in-session agents, one repetition per cell)

Executed inside a Claude Code session with no API key, following agent-loop's learning-effect Run 1 method. Each run
was a fresh general-purpose agent of the same model as the session, with no memory of the conversation. Every run
got the identical instruction:
- work only in this workspace, with no network;
- follow the repository's agent instructions;
- do not commit;
- report what you changed.

The task text followed. All 12 ran in parallel, and no human intervened. Per-run data:
[`route-experiment.results.jsonl`](route-experiment.results.jsonl).

| Case | A native | B tools, unmentioned | C tools + guidance |
| --- | --- | --- | --- |
| `fixture-rename` | correct, native | correct, native | correct, native |
| `fixture-remove` | correct, native | correct, native | correct, native |
| `fixture-body` | correct, native | correct, native | correct, **direct** (`agent-edit edit` + `verify`) |
| `recall-rename` | correct, native, no new test failures | correct, native, no new test failures | correct, native, no new test failures |

| Arm | Correct | Unintended changes | agent-map / agent-edit calls | Mean tokens | Mean tool calls | Mean seconds |
| --- | --- | --- | --- | ---: | ---: | ---: |
| A | 4/4 | 0 | n/a | 63,931 | 4.25 | 16.5 |
| B | 4/4 | 0 | 0 / 0 | 63,763 | 4.00 | 15.3 |
| C | 4/4 | 0 | 0 / 2 (one run) | 66,039 | 4.00 | 16.7 |

**What this shows:**

- **Ceiling effect.** All 12 agents produced the correct change and avoided every trap: `Cart::total()` called on
  the same line, the SQL string, the array key and the comment. All three `recall-rename` runs left the suite with no failure beyond the baseline's one
  environment failure, so it still exits nonzero. No native agent took the replace-everywhere
  shortcut that breaks the code in the route benchmark. With this model and these tasks, the tools cannot improve
  correctness, so this run cannot show an effectiveness gain in either direction.
- **Unprompted, the tools go unused (B: 0/4).** One B agent noticed `tools/route-tools` and still edited by hand.
  Installing the tools alone changes nothing.
- **With guidance, the tools are used where they help least.** The only use in arm C was a direct
  `agent-edit edit` (plus `verify`) for the local body change, the case where the route benchmark shows native
  editing is cheaper. No agent used agent-map, not even for the two renames the hypothesis assigns to Map + Edit. One
  C agent said the removal plan needs PHPStan; the runtime has PHPStan installed, so this was the agent's own
  assumption, not a missing capability.
- **Guidance costs tokens without a quality gain here.** C used about 3% more tokens than A, close to the 3.2 KB of
  guidance it reads. That difference is small next to the roughly 62k tokens of fixed agent overhead in every run.
  With n=1 per cell, the differences in tokens, tool calls and time are noise.
- **For the routing hypothesis:** this run gives no evidence for adding routing or more guidance, and some against
  it. The one guided choice went against the hypothesis. Whether Map + Edit pays off is untested, because no agent
  needed it here.

**Confounds and deviations, all recorded:**

- **Separation.** All agents shared one machine and were confined to their workspace by instruction only, with no
  sandbox. The shared tool runtime (agent-edit 0.8.0 with agent-map 0.24.0 in its vendor directory) hashed
  identically before and after the runs.
- **Tools without Composer.** Composer could not download here. Arms B and C got logging wrappers around one prepared
  runtime (`prepare.py --tools-runtime`), and the route is read from those logs (`tool-calls.log`, outside the
  workspace), not from the agent's own account. Preparing arm C first logged its own `instructions` call into those
  logs. Those preparation lines were removed before grading, and `prepare.py` now calls the runtime directly for
  that step.
- **Recall suite.** The workspace got a vendor shim (`--vendor-shim`) pointing at the same runtime plus agent-learning
  0.19.0. The suite runs; the one baseline failure (`AgentLearningNoteProjectionSourceTest`) comes from this
  environment and is excluded through the recorded baseline failures. PHPStan was not available in the Recall
  workspace, and two agents noted that. One agent needed `COMPOSER_ALLOW_SUPERUSER=1` to start `composer ci`.
- **Usage numbers.** Tokens, tool calls and duration come from the host's per-agent usage report, recorded by the
  operator in each `run.json`. They are not from a stream-json transcript.
- **Model.** The agents are the same model as the operating session, and the tasks may be familiar from training.
- **One extra change.** `recall-rename` A added a CHANGELOG entry for the public rename. That path is allowed, so it
  does not count as unintended.

**Next useful experiment.** Like the pipefail run, this one can only show an effect on tasks where native editing
fails. Candidates are:
- a rename with many call sites across many files;
- same-named methods across a class hierarchy;
- dynamic or `callable` references;
- a stale read, where the file changes between reading and editing.

Until such a task exists, more runs on these cases measure only overhead.

### Run 2 (2026-11-19, harder cases, two repetitions per cell)

Run 2 is the "next useful experiment" above: same-named methods across a class hierarchy, and a rename with many
call sites in many files. Method, instruction and isolation are those of Run 1. agent-edit is at 0.8.1 (see
Follow-ups for why), agent-map at 0.24.0. All 12 runs went in parallel. Per-run data: the `"run": 2` rows in
[`route-experiment.results.jsonl`](route-experiment.results.jsonl).

**Route check before the runs.** On `hierarchy-rename`, the operator ran the guided Map + Edit route once in an arm C
workspace: `build`, `rename-plan`, `apply --dry-run`, `apply`, `refresh`, `verify`. It graded correct with route
`map+edit`. That run is not an experiment run, but it shows the route was usable. On `recall-collect-rename`,
`rename-plan` is blocked (follow-up 3), so arm C agents there could only have learned that the tool refuses.

| Case | A native | B tools, unmentioned | C tools + guidance |
| --- | --- | --- | --- |
| `hierarchy-rename` | 2/2 correct, native | 2/2 correct, native | 2/2 correct, native |
| `recall-collect-rename` | 2/2 correct, native, no new test failures | 2/2 correct, native, no new test failures | 2/2 correct, native, no new test failures |

| Case | Arm | Mean tokens | Mean tool calls | Mean seconds |
| --- | --- | ---: | ---: | ---: |
| `hierarchy-rename` | A | 69,371 | 3.0 | 25.9 |
| | B | 69,406 | 3.0 | 26.9 |
| | C | 70,692 | 3.5 | 26.5 |
| `recall-collect-rename` | A | 72,042 | 4.0 | 37.2 |
| | B | 72,528 | 4.5 | 38.0 |
| | C | 76,330 | 6.5 | 53.6 |

**What this shows:**

- **Still a ceiling.** All 12 runs were correct with no unintended change. All six `hierarchy-rename` agents found
  every family call by reading the receiver types: through return types, a closure parameter, a closure capture, a
  nullable local and `parent::`. Every one left `Coupon::amount()`, `GiftCard::amount()`, the property, the keys, the
  constant and the comment alone. None took the shortcut that calibration shows the token oracle catches. With about
  15 files of fixture or about 60 sites in 25 files, reading is cheap enough for this model to rename by hand.
- **Not one agent-map or agent-edit call, in any arm.** The wrapper logs stayed empty. Both `hierarchy-rename` C
  agents said they had read the guidance and chose `sed` or hand edits over "the optional" tools. Arm C named the
  tools as optional, as the experiment design requires; in these runs that wording was enough to pass them over.
- **Guidance costs more on the large case.** On `recall-collect-rename`, C used 6% more tokens and 44% more time than
  A, with no difference in correctness. Across Run 2 the overhead was 4%, against 3% in Run 1.
- **For the routing hypothesis:** across both runs, 24 agents, no agent-map call on any task. On tasks this
  model can do by reading, that argues against routing or more guidance. Whether Map + Edit pays off on tasks too
  large to read remains untested. So does a stale read, the remaining candidate from Run 1. A further point: the
  route itself was broken for interface renames until 0.8.1, and no agent run would have shown it, because no agent
  tried the route.

**Confounds and deviations** are those of Run 1, plus:

- **Inherited host instructions.** The agents ran inside the operator's session and some saw that session's project
  instructions (the voku/agent-loop router, with `bin/agent-loop` and `composer ci`). One B agent quoted them and
  skipped them because the workspace has neither. That is outside the arm design; it reached every arm alike.
- **Fixture scope.** `hierarchy-rename` avoids nullsafe calls and first-class callables on the family, because
  agent-map 0.24.0 refuses or blocks both (follow-ups 1 and 2). With them, the Map route would have been unusable,
  and the case would have measured a tool defect instead of route choice.
- **Recall suite.** The one baseline failure (`AgentLearningNoteProjectionSourceTest`) remains and is excluded as in
  Run 1. The vendor shim now also provides `vendor/bin/phpstan`; every Recall agent ran it and got no errors.

#### Follow-ups found while preparing Run 2

Each was found by driving the Map + Edit route on the Run 2 cases. None was found by an agent run. With agent-map
0.24.1, `recall-collect-rename` is a safe plan of 62 edits in 25 files, and the guided route grades correct with the
suite green. One gap remains: `parameter-rename-plan` still blocks on anonymous implementations.

| # | Owner | Defect | Status |
| --- | --- | --- | --- |
| 0 | agent-edit | A safe `method_rename_plan` for an interface or overridden method was always refused at apply ("not bound to the declared target identity"): family-bound edits were accepted only for parameter renames. The hierarchy rename, the core Map + Edit use case, could not be applied at all. | Fixed in 0.8.1 (#73), with an end-to-end regression test. |
| 1 | agent-map | A nullsafe call `$repo->maybe()?->amount()` on a family receiver is recorded twice: correctly resolved, and as `dynamic` with receiver `Product\|null`. The dynamic copy marks the plan `review_required`. | Fixed in agent-map 0.24.1 (voku/agent-map#202). |
| 2 | agent-map | A first-class callable `$bundle->amount(...)` with a resolved receiver blocks the rename: "building a callable is not a call relation". The receiver type is known, so the reference is rewritable. | Fixed in agent-map 0.24.1 (voku/agent-map#202). |
| 3 | agent-map | An interface method implemented by an anonymous class (`new class implements RecallProvider`, here in Recall's tests) blocks the rename: "crosses an unindexed method contract". | Fixed in agent-map 0.24.1 (voku/agent-map#202). |
| 4 | kit | The Recall vendor shim had no PHPStan, so Run 1 agents could not run the case's static analysis. | Fixed in this run. |

### Run 3 (2026-11-20, a rename too large to read, two repetitions per cell)

Run 3 tests the remaining candidate from Run 2: a task too large to do by reading. The case is `scale-rename`. The
method, instruction and isolation are those of Runs 1 and 2. The tools are agent-edit 0.8.1 and agent-map at 0.24.2
source. All 6 runs went in parallel. Per-run data: the `"run": 3` rows in
[`route-experiment.results.jsonl`](route-experiment.results.jsonl).

**Route check before the runs.** The operator ran the guided Map + Edit route once on `scale-rename`. `build` and
`rename-plan` took about 2 s each and returned a safe plan of 247 edits (14 declarations, 227 calls, 6 `parent::`
calls). `apply`, `refresh` and `verify` reported clear residue, and the result was byte-identical to the expected tree
and graded correct.

| Arm | Correct | Unintended changes | agent-map / agent-edit calls | Mean tokens | Mean tool calls | Mean seconds |
| --- | --- | --- | --- | ---: | ---: | ---: |
| A | 2/2 | 0 | n/a | 80,470 | 4.5 | 33.2 |
| B | 2/2 | 0 | 0 / 0 | 80,320 | 5.5 | 42.3 |
| C | 2/2 | 0 | 1 / 0 (`agent-map --help`, one run) | 83,916 | 7.0 | 47.9 |

**What this shows:**

- **Still a ceiling, and a new way of reaching it.** All 6 runs changed exactly the 110 expected files, matched the
  expected tree by tokens and kept behaviour. With 4–7 tool calls per run, every agent applied its edits in bulk
  rather than site by site. Four reported a throwaway script that resolved each receiver through the navigators'
  return types and rewrote only the family's calls; two of them used PHP reflection. The two A runs did not describe
  their method. Every agent ran `run.php` to check. The task the tools were built for was done in 32–52 s, mostly with
  a tool the agent generated for the job.
- **Why the tools stayed unused here.** One C agent ran `agent-map --help` and then wrote its own script anyway. One B
  agent noticed `tools/route-tools` and skipped it because the wrapper "runs from a folder outside the repository",
  which the instruction forbade (see confounds). The other runs did not mention the tools.
- **Cost:** about 80k tokens per run against about 70k in Run 2. The task's size adds about 10k tokens; guidance adds
  another 4% (C against A). In this run C was also the slowest arm.
- **For the routing hypothesis:** this is the case the hypothesis assigns most clearly to Map + Edit, and the Map +
  Edit route did it in about 5 s of tool time. The agents matched its correctness by generating an equivalent
  resolver. That leaves no measured correctness gain to route towards. What remains is a difference in kind: the
  generated script has no verification receipt, provenance or fail-closed blind spots. On this fixture none of those
  were needed. They matter on code that reflection cannot load (side effects, missing autoloaders) or where a dynamic
  call hides a reference, which the fixture does not contain.

**Confounds and deviations**, in addition to those of Runs 1 and 2:

- **Tools outside the workspace.** In in-session mode the wrappers in `tools/route-tools/vendor/bin` call the shared
  runtime by an absolute path outside the workspace. With the instruction to work only inside the workspace, that
  path is a reason to avoid the tools, and one B agent said so. Arms B and C are therefore biased against tool use in
  this mode. Composer-installed arms (`prepare.py` without `--tools-runtime`) do not have this problem.
- **Scripts in the system temp directory.** Several agents kept their resolver script in the session's temporary
  directory, which the instruction allows. The scripts are not part of the workspace, and grading ignores them.
- **Fixture loads cleanly.** `scale-rename` has no side effects at class load, so reflection is safe to use on it. Real
  code bases often do not allow that.

### Calibration

CI runs `calibrate.py` on every change. Calibration success is not an experiment result.

## Limitations

- Seven cases, five of them generated or small fixtures. They show where the routes differ, not how often each situation
  occurs in real work. Each cell has one or two runs.
- Arm B measures unprompted discovery of tools that nothing mentions. A host that announces its tools differently
  sits between B and C.
- The model may know refactoring idioms or these packages from training; a strong arm A is informative, not a
  setup failure.
- The real-code case is a designed rename on a real code base, not a replayed historical change (see above).
